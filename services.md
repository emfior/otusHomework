# Карточки микросервисов

Использован **Microservices Canvas** со слайда 68 презентации. Каждая карточка содержит все его разделы; границы ответственности и вопросы развития добавлены явно. Обозначения API раскрыты в [contracts.md](contracts.md). Издатель события не вызывает потребителя напрямую: доставка идёт через RabbitMQ.

## 1. Identity Service — управление доступом

| Раздел Canvas | Описание |
| --- | --- |
| Назначение | Регистрация, вход и предоставление подтверждённой информации о пользователе и его правах |
| Задачи потребителей | Покупатель входит в систему; администратор назначает роли; остальные сервисы проверяют права пользователя |
| Зона ответственности | Учётные записи, пароли, сессии, роли `CUSTOMER`, `EMPLOYEE`, `COURIER`, `MANAGER`, `NETWORK_ADMIN`, область доступа `storeIds` |
| Данные | Identity Database: аккаунты, хеши паролей, refresh-сессии, назначения ролей, ключи подписи |
| Правила | Саморегистрация выдаёт только `CUSTOMER`. Привилегии назначает администратор сети. Сервисы проверяют подпись, срок, issuer/audience токена и доступ к магазину; одного знания `storeId` недостаточно |
| Запросы | `GET /api/v1/me`, OIDC discovery, `GET /.well-known/jwks.json` |
| Команды | `POST /api/v1/registrations`, OIDC вход/обновление/выход, `PUT /api/v1/users/{userId}/access` |
| Сервисные зависимости | Бизнес-сервисов нет. Валидность магазина при назначении доступа проверяет UI через Franchise; сервисы в любом случае проверяют существование своих объектов |
| Подписки на события | Нет |
| Публикуемые события | Нет в текущем объёме; обновление прав применяется при выдаче следующего короткоживущего токена |
| Качества | Защита учётных данных, аудит назначения прав; проверка JWT по кешированным ключам не требует сетевого запроса на каждую бизнес-операцию |
| За границей | Заказы, платёжные реквизиты, адреса доставки, рабочее состояние курьера |
| Развитие | Федерация с внешним Identity Provider; немедленный отзыв доступа потребует отдельного механизма, сейчас задержка не более 5 минут |

## 2. Product Service — меню и стоимость товаров

| Раздел Canvas | Описание |
| --- | --- |
| Назначение | Предоставлять ассортимент магазина и достоверный расчёт стоимости выбранных блюд |
| Задачи потребителей | Покупатель просматривает меню; управляющий изменяет цены и доступность; Order получает снимок позиций для заказа |
| Зона ответственности | Общий каталог, категории, переводы, меню конкретного магазина, базовая цена, признак доступности, расчёт суммы товаров |
| Данные | Product Database: продукты, категории, позиции меню с ценой/валютой/версией; краткоживущие расчёты `productQuoteId` |
| Правила | Цена принадлежит Product. Количество — положительное целое. Все позиции расчёта принадлежат одному магазину и валюте. Скидку рассчитывает Franchise по серверным ценам; Product проверяет границы скидки и возвращает `subtotal - discount = itemsTotal` |
| Запросы | `GET /api/v1/stores/{storeId}/menu`, `GET /api/v1/products/{productId}` |
| Команды | `POST/PATCH /api/v1/products[/{productId}]`, `PUT /api/v1/stores/{storeId}/menu/{productId}`, `POST /internal/v1/product-quotes`, `POST /internal/v1/availability-checks` |
| Сервисные зависимости | Franchise: сведения о магазине/валюте и `POST /internal/v1/promotion-evaluations`; Identity: ключи проверки токенов |
| Подписки на события | Нет; актуальная коммерческая политика запрашивается при расчёте |
| Публикуемые события | Нет в текущей версии: подписчиков на изменения меню пока нет |
| Качества | Независимое масштабирование чтения меню, локализация, повторная проверка доступности при оформлении; кеш меню не используется как источник окончательной суммы |
| За границей | Жизненный цикл заказа, списание денег, управление правилами акций, складские остатки ингредиентов |
| Развитие | Поиск и склад можно подключить позднее; наличие в меню не обещает резерв ингредиентов |

## 3. Franchise Service — магазины и политика сети

| Раздел Canvas | Описание |
| --- | --- |
| Назначение | Управлять независимыми франшизами и правилами работы магазинов в рамках сети |
| Задачи потребителей | Покупатель выбирает магазин и видит акции; управляющий настраивает магазин; администратор сети задаёт национальные акции |
| Зона ответственности | Владельцы франшиз, магазины, страна, адрес/координаты, расписание, часовой пояс, валюта, разрешённые способы оплаты, параметры кухни и доставки; создание и применение акций |
| Данные | Franchise Database: магазины и владельцы, версии настроек, национальные и локальные акции |
| Правила | Управляющий меняет только свой магазин и его локальные акции. Национальную акцию задаёт администратор. Акция действует в стране/магазине и в локальном временном интервале. Применяется одна наиболее выгодная акция. Скидка не превышает стоимость товаров |
| Запросы | `GET /api/v1/stores`, `GET /api/v1/stores/{storeId}`, `GET /api/v1/promotions?storeId=...` |
| Команды | `POST /api/v1/stores`, `PATCH /api/v1/stores/{storeId}`, `POST/PATCH /api/v1/promotions[/{promotionId}]`, `POST /internal/v1/promotion-evaluations` |
| Сервисные зависимости | Identity: проверка прав. Доступ к Product для применения акции не нужен: доверенный Product передаёт состав и базовые суммы |
| Подписки на события | Нет |
| Публикуемые события | Нет; потребители запрашивают необходимые настройки синхронно |
| Качества | Изоляция франшиз; явные страна, валюта, часовой пояс; воспроизводимость расчёта по сохранённым версиям правил |
| За границей | Базовые цены и доступность блюд, текущая очередь кухни, назначение курьера, фактическое состояние платежа |
| Развитие | При усложнении маркетинга правила и расчёт акций выделяются в отдельную бизнес-возможность |

## 4. Order Service — корзина, заказ и кухня

| Раздел Canvas | Описание |
| --- | --- |
| Назначение | Превращать намерение покупателя в исполненный заказ и показывать его состояние |
| Задачи потребителей | Покупатель оформляет и отслеживает заказ; сотрудник ведёт очередь кухни, готовит, выдаёт или отклоняет заказ |
| Зона ответственности | Корзина, предложение оформления, неизменяемый снимок покупки, оркестрация создания платежа, очередь кухни, `readyAt`, переходы заказа, отмена |
| Данные | Order Database: корзины/версии, checkout quotes, заказы и позиции-снимки, статусы оплаты/доставки как проекции, outbox/inbox, незавершённые шаги оформления |
| Правила | Одна корзина — один магазин. Итог равен стоимости товаров Product плюс тарифу Delivery. Пара способов получения/оплаты проверяется сервером. ONLINE подтверждается только событием Billing. Отмена и начало приготовления конкурируют по версии заказа. Завершение требует оплаты и подтверждённой выдачи/доставки |
| Запросы | `GET /api/v1/carts/{cartId}`, `GET /api/v1/orders[/{orderId}]` (списки ограничены владельцем или магазином) |
| Команды | Управление корзиной; `POST /api/v1/checkout-quotes`, `POST /api/v1/orders`, `POST /api/v1/orders/{orderId}/payment-attempts`, `.../actions` |
| Сервисные зависимости | Product: стоимость и доступность; Franchise: приём заказов и параметры приготовления; Delivery: тариф/проверка зоны; Billing: платёж и повтор оплаты; Identity: права |
| Подписки на события | Billing: `PaymentSucceeded`, `PaymentFailed`, `RefundStatusChanged`; Delivery: `DeliveryAssigned`, `DeliveryAssignmentFailed`, `DeliveryPickedUp`, `DeliveryDelivered`, `DeliveryFailed`, `DeliveryCancelled` |
| Публикуемые события | `OrderConfirmed`, `OrderReady`, `OrderCancelled` |
| Качества | Идемпотентное оформление; отсутствие общей распределённой транзакции; восстановление незавершённых шагов; стабильная сумма покупки и история переходов |
| За границей | Формулы скидок, API платёжного провайдера, управление курьерами, алгоритмы маршрутизации |
| Развитие | Кухня выделяется при независимом развитии производства; сейчас `readyAt` считается здесь по очереди и настройкам Franchise |

Прогноз готовности: Order распределяет подтверждённые заказы по `parallelOrders` виртуальным рабочим местам, учитывает оставшееся время готовящихся заказов и длительность нового заказа `baseMinutes + perItemMinutes × quantity`. `readyAt` — ближайшее возможное окончание; это оценка, а не обещание точного времени. Перед оплатой оценка предварительная, после подтверждения пересчитывается по очереди. Изменение параметров кухни применяется к новым оценкам, фактические переходы фиксирует сотрудник.

## 5. Billing Service — платежи и возвраты

| Раздел Canvas | Описание |
| --- | --- |
| Назначение | Принимать деньги за заказ и учитывать возвраты независимо от способа оплаты |
| Задачи потребителей | Order создаёт платёж на согласованную сумму; покупатель платит онлайн; сотрудник/курьер фиксирует наличные; отмена запускает возврат |
| Зона ответственности | Платёжные обязательства, попытки онлайн-оплаты, адаптер провайдера, обработка подписанных callbacks, фиксация наличных, полный возврат, сверка неизвестных результатов |
| Данные | Billing Database: платежи, попытки, provider reference, кассовые подтверждения, возвраты, отменённые `orderId`, outbox/inbox |
| Правила | Сумма и валюта приходят только из Order и не изменяются браузером. Один платёж на заказ, новая попытка не меняет сумму. Успех устанавливается по проверенному провайдеру или разрешённой операции учёта наличных. Отмена с поздним списанием требует возврата. Полные карточные данные не хранятся |
| Запросы | `GET /api/v1/payments/{paymentId}`; `GET /internal/v1/payments/by-order/{orderId}` для восстановления оформления |
| Команды | `POST /internal/v1/payments`, `.../{paymentId}/attempts`, `POST /api/v1/payments/{paymentId}/cash-receipts`, `.../cash-refunds`, `POST /callbacks/v1/payments/{provider}` |
| Сервисные зависимости | Внешний платёжный провайдер; Identity. Нет запросов к меню, акциям или БД Order |
| Подписки на события | `OrderCancelled` от Order |
| Публикуемые события | `PaymentSucceeded`, `PaymentFailed`, `RefundStatusChanged` |
| Качества | Идемпотентность, финансовый аудит, сверка с провайдером, безопасный повтор запросов; данные денег выражаются целыми минимальными единицами валюты |
| За границей | Расчёт цен/скидок, управление заказом, подтверждение готовности или вручения |
| Развитие | Выбор платёжного адаптера по стране; интеграция касс; налоги и фискализация требуют уточнения бизнес-правил |

## 6. Delivery Service — выполнение доставки

| Раздел Canvas | Описание |
| --- | --- |
| Назначение | Доставлять подтверждённый заказ от магазина получателю |
| Задачи потребителей | Покупатель узнаёт доступность и стоимость доставки; курьер получает назначение и завершает его; сотрудник видит проблемы назначения |
| Зона ответственности | Проверка адреса по зоне, тариф доставки, активность курьеров, заявка, атомарное назначение свободного курьера, забор, вручение и ошибки доставки |
| Данные | Delivery Database: расчёты тарифа, курьеры/занятость, доставки, снимки адресов и контакта, признак готовности, проекция оплаты, outbox/inbox |
| Правила | Одна доставка на `orderId`; только `DELIVERY`. Курьер и доставка относятся к одному магазину. Только назначенный курьер меняет выполнение и фиксирует наличные. Забор разрешён после `OrderReady`, завершение — после оплаты. Отмена освобождает курьера. Терминальные состояния не откатываются поздними событиями |
| Запросы | `GET /api/v1/deliveries[/{deliveryId}]`, `GET /api/v1/deliveries/{deliveryId}/route` |
| Команды | `POST /internal/v1/delivery-quotes`, `POST /internal/v1/delivery-checks`, `PUT /api/v1/couriers/me/availability`, `POST /api/v1/deliveries/{deliveryId}/actions`, `.../cash-payment` |
| Сервисные зависимости | Franchise: зона, тариф, адрес магазина; Map: маршрут; Billing: фиксация наличных; Identity: права |
| Подписки на события | Order: `OrderConfirmed`, `OrderReady`, `OrderCancelled`; Billing: `PaymentSucceeded` |
| Публикуемые события | `DeliveryAssigned`, `DeliveryAssignmentFailed`, `DeliveryPickedUp`, `DeliveryDelivered`, `DeliveryFailed`, `DeliveryCancelled` |
| Качества | Уникальное назначение, восстановление после повторов, изоляция персональных данных получателя; недоступная карта не блокирует фиксацию статуса |
| За границей | Кухня, создание заказов, обработка онлайн-платежей, хранение банковских реквизитов |
| Развитие | Подключение внешней курьерской службы через адаптер; сложная диспетчеризация и возврат после неудачного вручения — следующие процессы |

## 7. Map Service — навигация

| Раздел Canvas | Описание |
| --- | --- |
| Назначение | Давать маршрут и время в пути с учётом пробок через единый контракт |
| Задачи потребителей | Покупатель едет за заказом, курьер — к получателю |
| Зона ответственности | Адаптеры минимум двух внешних картографических провайдеров, выбор по региону, таймауты и переключение, нормализация маршрута |
| Данные | Постоянной БД нет; допускается краткоживущий кеш маршрутов без долговременного хранения геолокации |
| Правила | Запрос задаёт координаты начала и либо `storeId`, либо координаты назначения. Возвращаются источник, время расчёта и признак учёта пробок. При отказе обоих провайдеров — явная ошибка, без выдуманного ETA |
| Запросы | `GET /api/v1/routes?origin=...&storeId=...` (самовывоз) либо `...&destination=...` (доставка) |
| Команды | Нет: построение маршрута не меняет бизнес-состояние |
| Сервисные зависимости | Franchise: координаты магазина для самовывоза; внешние Mapping Provider A/B; Identity: проверка токенов внутренних клиентов |
| Подписки на события | Нет |
| Публикуемые события | Нет |
| Качества | Независимость от конкретного поставщика карт, деградация до показа адреса, минимизация передачи геолокации |
| За границей | Срок приготовления, стоимость доставки, назначение курьера, жизненный цикл заказа |
| Развитие | Региональные провайдеры и способы передвижения добавляются за единым API; конкретных поставщиков выбирают по покрытию страны |

## Остальные контейнеры

**Web Application** — адаптивный серверный веб-интерфейс для всех ролей (HTML/CSS/JavaScript и BFF). Маршрутизирует пользовательские действия к сервисам, хранит защищённую сессию, показывает состояния и ошибки. Не принимает решений о цене, оплате и допустимости переходов; сервисы повторно проверяют права. Это контейнер приложения, а не восьмой бизнес-микросервис.

**Базы данных** принадлежат своим сервисам. **Payment Provider** и два **Mapping Provider** — внешние программные системы. RabbitMQ показан на логических асинхронных связях; его развёртывание относится к инфраструктуре, а не к декомпозиции бизнес-возможностей.
