# Декомпозиция микросервисов: I'll Have the BLT

Архитектура интернет-магазина сети сэндвичных по кате [I'll Have the BLT](https://nealford.com/katas/kata?id=BLT). Решение охватывает заказ, приготовление, самовывоз и доставку, оплату и управление франшизами. Это проект архитектуры, реализация сервисов в репозитории отсутствует.

## Выбранный паттерн

**Decompose by business capability — разбиение по бизнес-возможностям**, рассмотренное на слайдах 47–50 презентации. Границы соответствуют устойчивым функциям бизнеса и сохраняются при изменении интерфейса, провайдера платежей или страны работы.

| Бизнес-возможность | Сервис | Какие изменения локализуются |
| --- | --- | --- |
| Управление доступом | Identity Service | Способы входа и роли сотрудников |
| Управление предложением магазина | Product Service | Меню, базовые цены, доступность, расчёт стоимости позиций |
| Управление франшизами и коммерческой политикой сети | Franchise Service | Магазины, режим работы, национальные и локальные акции |
| Приём и выполнение заказа | Order Service | Корзина, оформление, очередь кухни, прогноз готовности, жизненный цикл заказа |
| Приём и возврат оплаты | Billing Service | Онлайн-провайдеры, учёт оплаты при получении, возвраты |
| Организация доставки | Delivery Service | Зона доставки, тариф, назначение курьера, движение доставки |
| Навигация | Map Service | Выбор картографического провайдера, маршруты с учётом пробок |

Identity — обеспечивающая возможность, Map — интеграционная граница навигации. Map выделен из-за работы с несколькими картографическими системами и расширения географии. Это не разбиение по техническим слоям: каждый бизнес-сервис владеет своим поведением и своими данными.

Корзина и заказ остаются в Order: превращение корзины в заказ требует общего снимка состава и проверки версии. Кухня на первом этапе также входит в Order: там находятся очередь и время приготовления. Billing отделён, поскольку состояние платежа и платёжные интеграции меняются независимо от кухни. Акции пока входят во Franchise вместе с областью их действия; отдельный Promotion Service потребуется при существенном усложнении правил.

## Предметная модель и границы данных

Покупатель формирует корзину **одного магазина**. Из неё создаётся заказ со снимком позиций, цен, скидок и адресов. Заказ связан с платежом, а при доставке — ещё и с доставкой. Магазин принадлежит владельцу франшизы; меню и акции имеют область действия. Сотрудник готовит заказ, назначенный курьер выполняет доставку.

| Понятие | Единственный владелец | Использование в других контекстах |
| --- | --- | --- |
| Учётная запись, роль, разрешённые магазины | Identity | Подписанные claims доступа |
| Продукт, меню магазина, базовая цена, доступность | Product | Снимок позиций в Order |
| Магазин, владелец франшизы, расписание, настройки кухни и доставки, акция | Franchise | Снимок настроек при оформлении; результат применения акций в Product |
| Корзина, предложение оформления, заказ, очередь кухни, `readyAt` | Order | События для Billing и Delivery |
| Платёж, факт получения денег, возврат | Billing | Проекция платёжного статуса в Order и Delivery |
| Заявка на доставку, назначенный курьер, статус доставки | Delivery | Проекция статуса в Order |
| Маршрут и оценка времени в пути | Map | Временный результат для интерфейса и Delivery |

У шести сервисов есть собственные логические БД. Только владелец обращается к своей БД; общих таблиц и межсервисных SQL-запросов нет. Map не требует постоянного хранилища. Физическое размещение БД не задаётся этой диаграммой. Снимок в заказе фиксирует условия покупки и не заменяет источник текущих цен.

## Уточнения и допущения

Требования к мобильному доступу, акциям, картам, вариантам получения и оплаты взяты из [исходной каты](https://nealford.com/katas/kata?id=BLT). Следующие решения приняты для конкретизации учебного проекта:

- Меню доступно без входа, оформление требует учётной записи. Заказы из разных магазинов оформляются отдельно.
- Получение: `PICKUP` или `DELIVERY`. Оплата: `ONLINE`, `AT_PICKUP` или `ON_DELIVERY`. Допустимы пары `PICKUP + ONLINE/AT_PICKUP` и `DELIVERY + ONLINE/ON_DELIVERY`.
- Доступность блюда — признак продажи, а не учёт ингредиентов. Резервирование склада вне текущего объёма. Если блюдо закончилось после проверки, сотрудник отклоняет заказ до приготовления; оплаченный заказ возвращается.
- Онлайн-заказ передаётся кухне после оплаты; заказ с оплатой при получении — после оформления. Отмена допустима до `PREPARING`. Поздние претензии и частичные возвраты требуют отдельного бизнес-процесса.
- Доставка выполняется курьерами магазина. Автоматического назначения свободного курьера достаточно для первой версии; невозможность назначения видна сотруднику.
- Оплата при получении фиксируется как наличная; подключение кассового терминала — дальнейшее расширение Billing.
- Национальные акции имеют `countryCode`, локальные — `storeId`. Акции не складываются: применяется одна с максимальной скидкой; при равенстве — с меньшим `promotionId`. Лояльность и индивидуальные купоны не включены.
- Имеющийся факс сохраняется вне системы. Сотрудник может внести такой заказ через рабочий интерфейс для учёта в очереди кухни; автоматического распознавания факсов нет.
- Обновления статуса отображаются периодическим запросом веб-интерфейса. SMS, email и отдельный сервис уведомлений не требуются.

Это допущения решения, а не дополнительные требования автора каты. Java/Spring Boot, PostgreSQL и RabbitMQ на диаграмме — предлагаемые технологии, а не уже реализованный стек.

## Взаимодействие и согласованность

Синхронный HTTPS/JSON используется, когда следующий шаг требует немедленного результата: получить меню, рассчитать предложение оформления, создать платёжную сессию, построить маршрут. Order координирует оформление, но не рассчитывает скидки и не интегрируется с платёжным провайдером.

Изменения оплаты, заказа и доставки передаются асинхронно через RabbitMQ. На C4 связи подписаны `via RabbitMQ` и показаны пунктиром; направление — от издателя к потребителю. Такая запись сохраняет видимость зависимостей и соответствует [нотации C4 для сообщений](https://c4model.com/abstractions/queues-and-topics). Это логические связи, а не прямые HTTP-вызовы.

Внутри сервиса изменения атомарны. Между сервисами используется eventual consistency: локальная транзакция с outbox, повторная доставка, дедупликация и компенсации. Отмена заказа не означает мгновенный возврат денег; состояния заказа, платежа и доставки разделены. Гарантии и последовательности определены в [контрактах](contracts.md).

## Проверка на будущие изменения

| Изменение | Что меняется | Что сохраняется / ограничение |
| --- | --- | --- |
| Выход в другую страну | Franchise: страна, часовой пояс, переводы и акции; Product: меню и валюта; Billing/Map: региональные адаптеры | В контрактах есть `countryCode`, `timeZone`, `currency`, локаль. Налоги и фискализацию нужно уточнить перед запуском страны; конвертации валют нет |
| Рост до миллионов пользователей | Независимое масштабирование чтения меню, Order и Delivery; кеширование меню, разбиение нагрузки по магазинам | Оформление проверяет актуальные данные. SLO и число экземпляров требуют измерений |
| Замена или отказ картографического провайдера | Адаптер/правила выбора в Map | Заказ и кухня не зависят от доступности карты; интерфейс сохраняет адрес магазина |
| Новый способ оплаты | Billing и разрешённые способы для магазина | Order передаёт фиксированную сумму, не знает API провайдера |
| Сложная маркетинговая программа | Выделение Promotions из Franchise | Product запрашивает результат применения акций через версионированный контракт |
| Более сложная кухня | Выделение Kitchen из Order при появлении отдельных команд/нагрузки | Потребуется контракт очереди и готовности; сейчас лишняя распределённая транзакция не нужна |
| Внешняя курьерская служба | Адаптер в Delivery | Order получает те же события выполнения доставки |

Цена решения — сетевые отказы, задержки событий и сопровождение семи сервисов. При небольшой команде эти границы можно сначала реализовать модулями монолита (слайды 7–14); в ДЗ представлена целевая микросервисная декомпозиция.

## Просмотр диаграмм

Источник модели — [workspace.dsl](workspace.dsl). [workspace.json](workspace.json) — сгенерированный экспорт; вручную его редактировать не следует. `SystemContext` показывает роли и внешние системы, `Containers` — приложения, БД и взаимодействия. SVG находятся в [diagrams](diagrams).

Для интерактивного просмотра в использованной при проверке версии Structurizr Lite:

```sh
docker run --rm -p 8080:8080 -v "$PWD:/usr/local/structurizr" structurizr/lite:2025.11.08
```

Открыть `http://localhost:8080` и выбрать `Containers`. [tools/ExportWorkspace.java](tools/ExportWorkspace.java) и [инструкция экспорта](diagrams/README.md) позволяют повторить валидацию и экспорт из DSL.
